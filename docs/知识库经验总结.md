# 知识库经验总结（zhishiku 回写素材）

> 本次任务（2026-11-17 夜）为"局域网三机代码接力"新搭 DevSync 工具链。以下是从本次实战提炼的可复用教训，按 zhishiku 的「症状→根因→修复→教训」格式整理，供回写公开知识库（已脱敏：无令牌/密码/内网敏感信息，IP 为局域网私有地址）。

## 1. PowerShell 5.1 跨版本/跨进程的三个经典坑（一次全踩）

**症状**：脚本含中文就报错；git 输出莫名变成异常；函数返回值"污染"成数组。

**根因与修复**：
1. PS5.1 把无 BOM 文件当 ANSI 解析 → **所有含中文的 .ps1 必须带 UTF-8 BOM**；需要静默提权执行的脚本干脆纯 ASCII。
2. `$ErrorActionPreference='Stop'` 下，git 探测类命令的 stderr（如 rev-parse 的 `fatal:`）会变成 terminating error → git 调用统一走辅助函数（内部临时降级 EAP + 显式检查 `$LASTEXITCODE`）。
3. PowerShell 函数会把"输出流"和 `return` 值合并给调用方 → `$rc = Invoke-Git push` 时 $rc 是"输出行数组+退出码"，`if ($rc -ne 0)` 永远为真。**git 的过程输出必须用 Write-Host（宿主流），返回值才干净**。

**教训**：在 Windows 上写自动化 CLI，PowerShell 的流模型是第一坑源；"输出走宿主流、状态走返回值"是唯一稳的架构。

## 2. git autostash 冲突时退出码不可信

**症状**：`git pull --rebase --autostash` 报冲突但退出码 0，脚本继续执行并谎报成功，工作区实际残留未合并文件和 stash。

**根因**：合并本身成功（fast-forward 完成），只有 stash 应用冲突，git 不视为失败。

**修复**：退出码之外必须做**状态检查**：
- `git diff --name-only --diff-filter=U` 非空 → 有未合并文件
- `git stash list` 出现 `autostash` → 本地改动与远端冲突被暂存
- `.git/rebase-merge` 目录存在 → rebase 进行中

**教训**：对 git 的自动化判断，"退出码 + 工作区状态"双验才可靠；这也促成了 devsync 的防呆设计——冲突态下再次操作直接拒绝并给指引。

## 3. 跨进程编码错配毁掉一切文本断言

**症状**：测试断言匹配不到日志里肉眼可见的中文关键字；日志一半正常一半 mojibake。

**根因**：子进程（devsync）把控制台切成 UTF-8 输出，父进程（测试脚本）用系统默认 GBK 解码其 stdout；部分路径侥幸双次转换抵消，部分损坏。

**修复**：
1. 父进程 dot-source 时立即 `[Console]::OutputEncoding = UTF8`；
2. 更根本的：**CLI 输出机器可读的 ASCII 结果行**（`RESULT: OK / CONFLICT / ERROR`），断言只依赖 ASCII 行，中文仅供人读。

**教训**：中文环境下做"AI 自主闭环/脚本断言"，必须假设中文输出会被编码层破坏；机器可读结果行是唯一可信的契约。

## 4. 静默提权（无人值守 UAC）的可行路径

**症状**：管理员账号的 shell 里 `net session` 显示未提权（UAC 过滤令牌），`sc start` 服务被拒。

**核查**：注册表 `ConsentPromptBehaviorAdmin = 0`（提升免确认）+ `FilterAdministratorToken = 1`（默认过滤）组合。

**可行做法**：把需要提权的动作写成独立 .ps1（纯 ASCII），用 `Start-Process powershell -Verb RunAs -Wait -ArgumentList '-File',xxx` 静默提权执行。**嵌套引号的内联命令必然静默失败，必须走文件传参**。

**教训**：无人值守场景先探测 `ConsentPromptBehaviorAdmin`；提权脚本与普通脚本隔离，ASCII 化。

## 6. 方案层面的经验

- **映射盘假死是 SMB 模型固有的**（微软官方文档承认），社区补丁（保活/KeepConn/清残留）治标不治本；换"git over HTTP 中心枢纽"是根治，且顺带解决隐私（私库+禁注册+令牌+网段防火墙）和密钥同步（独立私库）。
- 自建 Gitea 的 Windows 部署社区教程很多，但都止步于"服务跑起来"；**面向"接力"语义的 CLI 封装（take/handoff）才是让三台电脑真正省心的关键**——工具的心智模型比工具本身重要。
